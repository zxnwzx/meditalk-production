# 메디톡 (MEDITOK) — 제약·바이오 전문지

"제약·바이오 업계의 목소리를 전합니다" — 실제로 동작하는 발행 시스템입니다.
기자가 관리자 사이트에서 기사를 쓰고 심사 요청을 하면, 편집장이 승인·발행한 기사만
공개 홈페이지에 노출됩니다.

## 🏗️ 실전 인프라 업그레이드 (이번 업데이트)

전부 실제로 PostgreSQL·Redis·S3 호환 서버를 로컬에 띄워서 검증한 뒤 반영했습니다. **환경변수를 안 넣으면 기존과 완전히 동일하게(SQLite·서버메모리·로컬디스크) 동작**하니, 지금 당장 뭘 새로 설정 안 하셔도 됩니다.

| 환경변수 | 안 넣으면 | 넣으면 |
|---|---|---|
| `DATABASE_URL` | SQLite 파일 사용 | PostgreSQL 사용 (`postgresql://user:pass@host:5432/dbname` 형식) |
| `REDIS_URL` | 서버 메모리로 로그인제한·캐시 관리 | Redis로 관리 (워커를 여러 개 띄워도 안전) |
| `S3_BUCKET` + `S3_ENDPOINT_URL` + `S3_ACCESS_KEY_ID` + `S3_SECRET_ACCESS_KEY` + `S3_PUBLIC_URL_BASE` | 로컬 `static/uploads` 폴더에 이미지 저장 (재배포 시 소실 위험) | S3 또는 Cloudflare R2에 이미지 저장 |

**S3/R2 쓰실 때 꼭 하셔야 하는 것**: 코드가 이미지를 올리는 것까지는 자동으로 하지만, **버킷을 "공개 읽기"로 설정하는 건 R2/S3 대시보드에서 직접 하셔야 합니다.** (보안상 기본값은 비공개이고, 이걸 코드가 자동으로 풀어버리면 오히려 위험합니다.) Cloudflare R2라면 버킷 설정에서 "Public Development URL"을 켜거나 커스텀 도메인을 연결한 뒤, 그 주소를 `S3_PUBLIC_URL_BASE`에 넣어주세요.

`Procfile`의 워커 수는 안전하게 1개로 맞춰뒀습니다. `REDIS_URL`을 설정하시면 `--workers 2` 이상으로 늘리셔도 로그인 제한·캐시가 꼬이지 않습니다.

### 자동 백업

`scripts/backup.py`를 하루 한 번 실행하도록 등록해 두면, `/admin/backup` 버튼을 안 눌러도 자동으로 백업됩니다 (SQLite면 파일 복사, PostgreSQL이면 `pg_dump`, `S3_BUCKET` 설정 시 S3에도 함께 올라가고 로컬은 최근 7개만 보관됩니다). Render라면 별도의 "Cron Job" 서비스로 다음 명령을 하루 1회 실행하도록 등록하세요:

```
python3 scripts/backup.py
```

PostgreSQL을 쓰신다면 이 크론잡 서비스에 `postgresql-client` 패키지가 설치되어 있어야 합니다(빌드 커맨드에 `apt-get install -y postgresql-client` 추가).

### 자동화 테스트

`tests/` 폴더에 53개의 자동화 테스트가 있습니다(로그인, 발행 워크플로우, 댓글, 이미지 업로드, 동시편집 충돌, 보안 취약점 등). 코드를 고치신 뒤에는 아래 명령으로 무엇이 깨졌는지 바로 확인할 수 있습니다:

```
pip install pytest
pytest tests/ -v
```

GitHub에 푸시할 때마다 자동으로 이 테스트가 돌아가도록 `.github/workflows/tests.yml`도 넣어뒀습니다.

## 🔤 이전 업데이트 — 리브랜딩 + 기능 전면 복원

**"명약명사"에서 "메디톡"으로 이름을 바꿨습니다.** 로고는 "메디"(검정) + "톡"(핑크-레드 그라데이션)입니다.

⚠️ **알아두셔야 할 것**: "메디톡"은 코스닥 상장사 **메디톡스(Medytox)**와 이름이 매우 유사합니다.
메디톡스는 같은 제약·바이오 업종에서 실제로 영업 중인 회사입니다. 이 이름으로 진행하기로
결정하셨다는 점을 이 README에도 기록해 둡니다 — 실제 서비스 오픈 전에 상표권 관련해서
한 번 더 검토해 보시는 것을 권합니다.

이번 업데이트에서 예전에 만들었던 기능들을 전부 다시 넣었습니다: 이미지 업로드, 태그, 댓글(+4자리
삭제 비밀번호), 댓글 신고, 오탈자 제보, 즉시발행/예약발행, 뉴스레터 관리, 기자 프로필 페이지,
정정보도 안내, 비밀번호 재설정, 관리자 통계 그래프, PWA(홈 화면 설치), 커스텀 에러 페이지.

작업 중 실제로 발견해서 고친 버그:
- `_invalidate_home_cache()` 함수가 호출만 되고 정의가 없던 문제
- 발행된 기사를 삭제하면 댓글·스크랩 때문에 DB 오류가 나던 문제 (사전 방지 처리)
- 이름을 바꾸며 생긴 어색한 조사("메디톡는" → "메디톡은")
- **`requirements.txt`에 Pillow 누락** — 예전에 실제 배포에서 이미지 업로드 500 에러를 냈던 원인과
  동일한 실수라, 이번엔 처음부터 넣었습니다
- 대시보드의 인라인 `onsubmit`이 새 CSP 정책과 충돌할 뻔한 것을 `site.js` 방식으로 교체

## ✅ 실제 사업에 즉시 활용하기 전 필수 체크리스트

아래 순서대로 진행하시면 됩니다. 코드/기능으로 지원되는 항목은 (✓ 구현됨)으로, 직접 처리하셔야 하는 항목은 (☐ 직접 진행)으로 표시했습니다.

### 1. 법적 기초 (직접 진행 — 뒤로 미룰수록 비쌉니다)
- ☐ 브랜드명 "메디톡" KIPRIS 상표 검색 및 필요시 변리사 확인
- ☐ 사업자등록 (개인사업자 또는 법인)
- ☐ 인터넷신문사업자 등록 (관할 시/도청) — **등록 완료 전까지 기사를 공개로 올리면 안 됩니다.** 실제 콘텐츠 채우기 전에 먼저 처리하세요.
- ☐ 등록 완료 후 `templates/base.html` 푸터의 "등록 준비중" 문구를 실제 등록번호로 교체

### 2. 계정·보안 (☐ 직접 진행, 코드는 ✓ 준비됨)
- ☐ `editor` / `reporter` 데모 비밀번호를 실제 비밀번호로 교체 → **`scripts/reset_for_launch.py` 실행 한 번으로 해결됩니다** (아래 설명)
- ☐ Render 환경변수에 `SECRET_KEY`(무작위 값), `SESSION_COOKIE_SECURE=1` 설정
- ✓ CSRF 보호, 로그인 시도 제한, 보안 헤더, 입력값 길이 제한 (지난 업데이트에서 적용 완료)

### 3. 데모 콘텐츠 정리 (✓ 스크립트 준비됨 — 반드시 실행)
지금 DB에는 한서바이오·청안제약 같은 **가상의 기업 기사**가 예시로 들어 있습니다. 이 상태로 실제 도메인에 올리면 독자에게 가짜 뉴스가 진짜처럼 보이게 되므로, 실제 오픈 전 반드시 아래를 실행해 정리하세요.

```bash
# 1) 먼저 백업 (관리자로 로그인 후 /admin/backup 에서 다운로드, 또는:)
python -c "import shutil; shutil.copy('meditok.db', 'myeongyak-backup.db')"

# 2) 데모 기사 삭제 + 계정 비밀번호 재설정을 한 번에
python scripts/reset_for_launch.py
```
실행하면 확인 문구(`RESET` 입력)를 거쳐 예시 기사를 전부 지우고, `editor`·`reporter` 계정의 새 비밀번호를 대화형으로 입력받습니다.

### 4. 검색 노출 (SEO) — ✓ 코드는 준비됨, 등록은 직접
- ✓ Open Graph / 트위터 카드 메타태그, 기사별 공유 미리보기 이미지
- ✓ `robots.txt`, `sitemap.xml` 자동 생성
- ✓ 검색·마이페이지 등 비공개성 페이지는 `noindex` 처리
- ☐ **[Google Search Console](https://search.google.com/search-console)** 에 도메인 등록 + sitemap.xml 제출
- ☐ **[네이버 서치어드바이저](https://searchadvisor.naver.com)** 에 등록 — 한국 사용자는 네이버 검색 비중이 훨씬 크므로 이쪽을 놓치면 안 됩니다.
- ☐ (선택) `templates/base.html`의 `naver-site-verification`, `google-site-verification` 메타태그에 각 서비스에서 발급하는 인증 코드 입력

### 6. 광고·협찬 영업 (✓ 코드는 준비됨)

- ☐ 아버님 기존 네트워크의 제약사 홍보팀 담당자들에게 창간 소식 + `/contact` 링크 전달

- **브랜드 리뉴얼**: 딥그린 + 와인 + 골드 팔레트로 전면 재디자인, 이주의 메디톡 PICK, 실시간 인기기사 랭킹, 검색 기능, 오피니언 스포트라이트, 세미나·채용 위젯.

## 동작 방식 (발행 워크플로우)

1. **기자**가 관리자 사이트(`/admin`)에서 "새 기사 작성" → 제목/섹션/부제/본문 입력
   - "임시저장" → 초안(draft) 상태로 저장, 본인만 확인 가능
   - "저장하고 심사 요청" → 대기(pending) 상태로 전환, 편집장 심사 큐에 노출
2. **편집장**이 `/admin/review`에서 대기 중인 기사를 확인하고 "발행" 또는 "반려"
3. 발행된 기사만 공개 홈페이지(`/`)와 기사 상세 페이지에 실시간으로 반영됩니다.
4. 편집장은 발행된 기사 중 하나를 "이주의 PICK"으로 지정할 수 있습니다.

## 계정 체계

- **독자(reader)**: 홈페이지에서 자유 가입.
- **기자(journalist)**: 편집장이 관리자 사이트 "기자 계정 관리"에서 생성. 발행 권한 없음.
- **편집장(editor)**: 기자 권한 전체 + 기사 발행/반려 + PICK 지정 + 기자 계정 생성 권한.

## 보안 — 이번에 코드에 직접 반영한 것들

- **디버그 모드 기본 OFF**: `debug=True`였던 것을 환경변수 `FLASK_DEBUG=1`을 명시적으로 켜지 않는 한 항상 꺼지도록 변경. 디버그 모드가 켜진 채 배포되면 에러 페이지를 통해 서버에서 임의 코드가 실행될 수 있는 심각한 취약점이라 가장 먼저 고쳤습니다.
- **CSRF 보호**: 로그인·회원가입·기사 작성/발행/반려/삭제·스크랩·뉴스레터 구독 등 데이터를 변경하는 모든 폼에 세션별 토큰을 심어, 다른 사이트에서 위조된 요청을 보내는 공격(CSRF)을 차단합니다.
- **로그인 무차별 대입 방지**: 같은 IP에서 5분 내 8회 이상 로그인 실패 시 일시적으로 차단합니다. (지금은 서버 프로세스 메모리 기반이라, gunicorn 워커가 여러 개면 워커별로 따로 집계됩니다 — 소규모 서비스엔 충분하지만 트래픽이 커지면 Redis 기반으로 교체 권장)
- **보안 헤더**: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`를 모든 응답에 추가. HTTPS 환경에서는 HSTS 헤더도 자동으로 붙습니다.
- **세션 쿠키 강화**: HttpOnly(자바스크립트로 쿠키 탈취 불가), SameSite=Lax(다른 사이트에서 쿠키 전송 방지) 적용. HTTPS 전용 쿠키는 배포 시 환경변수로 켤 수 있습니다.
- **입력값 길이 제한**: 제목·요약·본문·아이디 등에 서버 단 길이 제한을 둬서 비정상적으로 큰 요청으로 서버를 괴롭히는 것을 방지. 요청 본문 전체도 2MB로 제한.
- **로그인 세션 고정 공격 방지**: 로그인 성공 시 기존 세션을 정리하고 새로 발급.
- **SQL 인젝션**: 모든 쿼리가 처음부터 매개변수 바인딩(`?`) 방식이라 안전합니다 (문자열을 직접 이어붙이는 쿼리 없음).
- **XSS**: Jinja2 템플릿이 기본적으로 모든 출력값을 이스케이프하므로, 기자가 입력한 제목·본문에 스크립트를 넣어도 그대로 텍스트로 표시됩니다.

## 실제 배포 시 반드시 설정할 환경변수 (Render → Environment 탭)

| 변수명 | 값 | 설명 |
|---|---|---|
| `SECRET_KEY` | 무작위 긴 문자열 (예: `python -c "import secrets;print(secrets.token_hex(32))"` 로 생성) | 세션 암호화 키. 코드에 있는 기본값을 실서비스에 그대로 쓰면 안 됩니다. |
| `SESSION_COOKIE_SECURE` | `1` | 로그인 쿠키가 HTTPS로만 전송되도록 강제 (Render는 기본 HTTPS 제공) |
| `FLASK_DEBUG` | 설정하지 않음 (기본값 유지) | 절대 `1`로 설정하지 마세요. |

## 보안을 실제로 검증하는 방법

코드를 고치는 것과, "정말 안전한지 확인"하는 건 다른 작업이에요. 배포 후 아래를 해보시길 권합니다.

- **[securityheaders.com](https://securityheaders.com)** 에 도메인을 넣고 스캔 — 위에서 추가한 보안 헤더들이 실제로 응답에 붙어 나가는지 외부에서 확인할 수 있습니다.
- **[Mozilla Observatory](https://observatory.mozilla.org)** — 종합적인 웹 보안 점수를 매겨줍니다.
- **`pip-audit`** (`pip install pip-audit && pip-audit`) — 사용 중인 Flask 등 파이썬 패키지에 알려진 취약점(CVE)이 있는지 검사. 정기적으로(예: 월 1회) 돌려보시는 걸 추천합니다.
- **의심스러운 로그인 시도 모니터링**: Render 대시보드의 Logs에서 `400` 응답이나 `로그인 시도가 너무 많습니다` 메시지가 반복되면 공격 시도일 수 있습니다.
- 정말 제대로 하려면, 트래픽이 늘고 광고 수익이 붙기 시작하는 시점에 **외부 보안 점검(모의해킹) 1회**를 받는 것을 권합니다 — 프리랜서 보안 컨설턴트나 부트캠프 수준이 아닌 정식 업체 기준 수백만원대이지만, 회원 개인정보를 다루는 시점부터는 투자할 가치가 있습니다.

## 트래픽 대응 — 어느 시점에 뭘 해야 하나

**지금 (방문자 하루 수백 명 이하, Render 무료/스타터 플랜)**
- 지금 코드 그대로 충분합니다. 조회수·랭킹·티커 쿼리는 20초 캐시가 적용돼 있어 순간적으로 트래픽이 몰려도 DB를 매 요청마다 두드리지 않습니다.

**방문자가 늘기 시작하면 (하루 수천 명)**
- Render 유료 플랜(Standard 이상)으로 업그레이드 — 무료 플랜은 15분 무응답 시 서버가 잠들어서 첫 방문자가 느려집니다.
- `gunicorn` 워커 수를 늘리기: Procfile을 `web: gunicorn app:app --workers 3 --threads 2` 처럼 조정 (일반적으로 워커 수 = CPU 코어 수 × 2 + 1)
- SQLite → **PostgreSQL**로 전환 — SQLite는 동시 쓰기(기사 발행, 조회수 증가 등)가 많아지면 병목이 생깁니다. Render에서 PostgreSQL 애드온을 붙이고 `sqlite3` 코드를 `psycopg2` 기반으로 바꾸는 작업이 필요합니다 (원하시면 이 작업도 도와드릴 수 있어요).

**방문자가 더 늘면 (하루 수만 명 이상, 진짜 언론사 트래픽)**
- **Cloudflare**를 도메인 앞단에 무료로 붙이기 — 정적 리소스(CSS, 이미지)를 캐싱해 서버 부하를 크게 줄여주고, 기본적인 DDoS 방어도 덤으로 따라옵니다. 비용 없이 가장 효과가 큰 조치입니다.
- 지금의 메모리 기반 캐시·로그인 제한을 **Redis** 기반으로 교체 (서버 인스턴스가 여러 대로 늘어나면 메모리는 인스턴스마다 따로 놀기 때문)
- 이미지가 추가되면 Cloudflare Images나 S3 + CDN 조합으로 이미지 전송 최적화

이 순서대로 가면 트래픽이 늘 때마다 "지금 뭘 업그레이드해야 하는지"가 명확해서, 처음부터 과한 인프라에 돈 쓸 필요가 없습니다.
